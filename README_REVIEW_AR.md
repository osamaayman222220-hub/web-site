# CareNest — مراجعة وإصلاح أولي

## الملفات التي تم تعديلها أو إضافتها
- `js/supabase.js`: لا يحاول إنشاء حجز بحمولة مختصرة عند أخطاء RLS أو المفتاح الأجنبي أو الـ trigger؛ يعيد المحاولة المختصرة فقط عند أخطاء الأعمدة غير الموجودة. كما يمنع تمرير `nurse_profile_id` بدل `profiles.id` إلى `bookings.nurse_id`، ويُظهر رسالة أكثر فائدة عند فشل رفع الصورة، ويحذف ملف الصورة المملوك للمستخدم عند حذفها.
- `js/config.js`: تصحيح اسم التطبيق الظاهر من Raaya إلى CareNest.
- `sql/migration_v4_auth_profile_integrity.sql`: يصلح سببًا مهمًا محتملًا لوجود مستخدمين في `auth.users` دون صفوف في `profiles`: الدالة القديمة `handle_new_user()` كانت تلتقط كل الأخطاء وتكمل التسجيل بصمت. السكريبت يعيد إنشاء الدالة بدون ابتلاع الخطأ ويصلح الصفوف الناقصة الموجودة.
- `supabase/functions/save-national-id/index.ts`: أُضيفت Edge Function المطلوبة من `auth.js`. تتحقق من جلسة المستخدم، ولا تسجل الرقم القومي أو تخزنه كنص صريح، بل تخزن HMAC-SHA-256 باستخدام سر خادمي.

## الترتيب المقترح قبل الاختبار
1. خذ نسخة احتياطية من قاعدة البيانات الحالية.
2. تأكد أن `schema.sql` و`migration_v2_complete.sql` وأعمدة الحجوزات المطلوبة قد طُبقت سابقًا. لا تشغّل كل ملفات SQL عشوائيًا أو بترتيب غير معروف.
3. راجع `sql/migration_v4_auth_profile_integrity.sql` ثم شغّله في Supabase SQL Editor. يفترض أن مخطط V2 موجود بالفعل.
4. انشر Edge Function:
   `supabase functions deploy save-national-id`
5. عيّن أسرار الدالة في Supabase Functions Secrets: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, و`NATIONAL_ID_HASH_SECRET`. يجب أن يكون `NATIONAL_ID_HASH_SECRET` قيمة عشوائية طويلة وثابتة، ولا تضعها في ملفات الواجهة الأمامية.
6. اختبر تسجيل حساب جديد، ثم تحقق من وجود صف في `profiles`، ولحساب الممرض تحقق من وجود صف غير معتمد في `nurse_profiles`.
7. اختبر رفع صورة شخصية بحساب مسجل الدخول. تأكد أن Storage يحتوي على bucket باسم `profile-photos` وسياسات الرفع/التعديل/الحذف الصحيحة.
8. اختبر الخدمات والحجز بحساب مريض، ثم قبول/تحديث الحجز بحساب ممرض.

## تحذير أمني مهم
- لا تشغّل `sql/setup_and_fixes.sql` كما هو على بيئة إنتاج: يحتوي على سياسة تجعل جميع صفوف `profiles` قابلة للقراءة العامة، وقد تكشف البريد الإلكتروني والهاتف والعنوان.
- `sql/schema.sql` يحتوي أيضًا على سياسة قراءة عامة لـ `profiles`، وسياسة إدارة خدمات واسعة جدًا باسم `Admins can manage services` مع `using (true)` و`with check (true)`. يجب تضييق هذه السياسات قبل الإطلاق العام.
- لا تمنح أي مستخدم دور `admin` من واجهة التسجيل. استخدم إجراء إداري موثوقًا ومحدودًا.
- وجود مفتاح Supabase العام في `js/config.js` طبيعي للواجهة، لكن الأمان يعتمد على RLS وسياسات Storage. لا تضع مفتاح `service_role` في الواجهة.
- Edge Function الجديدة لم تُنشر تلقائيًا إلى مشروع Supabase، ولا يمكن التأكد من إعدادات مشروعك المباشر أو سياساته من ملف ZIP وحده.

## نتائج الفحص المحلي
- تم فحص 13 صفحة HTML ومراجع ملفات JavaScript/CSS المحلية؛ لم تظهر مراجع محلية مفقودة في الصفحات التي فُحصت.
- تم استخراج وفحص أكواد JavaScript المضمنة في صفحات HTML باستخدام `node --check`؛ لم تظهر أخطاء صياغة في الفحص المحلي قبل التعديلات، ويجب إعادة الاختبار بعد التعديلات.
- لم تُختبر عمليات Supabase الحية لأن ملف ZIP لا يحتوي على صلاحية اتصال بقاعدة البيانات أو بيئة تشغيل الموقع.
